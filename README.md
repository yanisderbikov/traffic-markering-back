# traffic markering — backend

Бэкенд площадки, где **заказчик** публикует объявления на рекламные интеграции,
а **криатор** берёт их в работу: снимает вертикальный ролик и прикрепляет на него ссылку.

Заказчик указывает ставку за 1000 просмотров, выделенный бюджет, порог вывода
(«вывод от 3 000 ₽» — с какой накопленной по объявлению суммы криатор может забирать
заработанное) и площадки, с которых принимает ролики (Instagram, TikTok, YouTube Shorts).
По мере набора просмотров бюджет «съедается»: на карточке объявления видно, сколько
выделено, сколько потрачено и сколько осталось. Все деньги — в рублях, а в БД и API —
**в копейках**.

Деньги заказчика лежат в **кошельке**: пополняет его менеджер финансов, а заказчик
распределяет свободный остаток между объявлениями — бюджет объявления резервируется
из кошелька, уменьшение бюджета возвращает разницу обратно. Пополнение и вывод
заказчику — переводы USDT (TRC-20) вне платформы: финансист заводит их со скриншотом
и номером транзакции, а заказчик подтверждает в своём кошельке.

Криатор зарабатывает на просмотрах: раз в сутки ночью начисленное по откликам
переезжает в его кошелёк — как только накопленное по объявлению дошло до его порога
вывода, — и он подаёт заявку на вывод в USDT (TRC-20).
Менеджер финансов переводит вручную, прикладывает скриншот и ссылку — криатор
подтверждает получение.

## Архитектура

Слои строго односторонние: `controller` → `service` → `repository`. Контроллер не
знает про JPA, сервис не знает про `JpaRepository`, а Spring Data не вылезает за
пределы `repository.impl`.

```
controller/                   @RestController, только разбор запроса и коды ответов
service/<область>/            public-интерфейс — то, что видят остальные слои
service/<область>/impl/       package-private @Service — реализация
repository/                   public-интерфейсы Getter*/Saver*/*Deleter
repository/impl/              package-private *Manager (@Component) и *Repo (@Repository)
model/                        @Entity
dto/                          то, что уезжает наружу
util/                         чистые функции без Spring
```

Зачем так:

- **Интерфейс отдельно от реализации.** Реализации сервисов объявлены без `public` —
  снаружи пакета их не видно, инжектится только интерфейс. Подменить реализацию
  (или замокать её в тесте) можно, не трогая вызывающий код.
- **`Getter*` / `Saver*` / `*Deleter` вместо одного репозитория на сущность.**
  Сервису, который только читает объявления, достаётся `GetterCampaign` — и он
  физически не может ничего записать. Права видны прямо в списке зависимостей класса.
- **`*Manager` — единственное место, где ловится сбой БД.** Каждый метод оборачивает
  вызов `*Repo` в `try/catch` и превращает любое исключение в
  `RuntimeException("Database exception", e)`, предварительно записав его в лог.
  Поэтому выше по стеку никто не разбирает `DataAccessException` и её наследников.
- **`*Repo` спрятан в `repository.impl`.** Интерфейс Spring Data package-private,
  так что мимо `*Manager` в базу не сходить — обход слоя не скомпилируется.

Исключение одно: `UserRepository` — обычный public `JpaRepository` прямо в
`repository`. Пользователь нужен почти каждому сервису, и заворачивать его
в четыре интерфейса смысла нет.

Ошибки бизнес-логики бросаются как
`ResponseStatusException(HttpStatus.X, "русское сообщение")` — текст уезжает
пользователю как есть, поэтому он сразу пишется по-русски. Ловят их локальные
`@ExceptionHandler` в каждом контроллере и заворачивают в `{"message": "..."}` —
формат, который фронт показывает без перевода.

## Роли

| Роль | Кто это | Что может |
|---|---|---|
| `CUSTOMER` | заказчик | заводит объявления, смотрит отклики, одобряет/отклоняет их, распределяет кошелёк по объявлениям |
| `CREATOR` | криатор | откликается на объявления с ссылкой на ролик, видит свои начисления, подаёт заявки на вывод USDT и подтверждает получение |
| `FINANCE_MANAGER` | менеджер финансов | видит кошельки всех заказчиков, заводит пополнения и выводы со скриншотами и номером транзакции; обрабатывает заявки криаторов на выплату |
| `ADMIN` | администратор | всё, что могут заказчик и криатор, плюс чужие объявления и отклики |
| `SUPER_ADMIN` | супер-админ | всё, что могут `ADMIN` и `FINANCE_MANAGER`, плюс скрытая ручка ролей `/api/superadmin/**` |
| `SERVICE` | не человек, а внешний анализатор просмотров | только `/api/tech/**` и `/api/actuator/**` |

Права наследуются: `Role.implied()` отдаёт набор ролей, которые подразумевает данная
(`SUPER_ADMIN` → `ADMIN`, `FINANCE_MANAGER`, `CUSTOMER`, `CREATOR`; `ADMIN` → `CUSTOMER`,
`CREATOR`). `JwtAuthFilter` кладёт в контекст authority на каждую из них, поэтому в
`WebSecurityConfig` достаточно `hasRole("FINANCE_MANAGER")`, а `CurrentUserService.require(role)`
пропускает всех, чья роль подразумевает нужную.

`SUPER_ADMIN` **не назначается через API**: единственный источник — `SUPER_ADMIN_EMAIL`.
`SuperAdminBootstrap` на старте заводит учётку с этой почтой (или поднимает существующую)
и понижает до `ADMIN` всех остальных с ролью `SUPER_ADMIN`. Остальные служебные роли
(`FINANCE_MANAGER`, `ADMIN`) супер-админ раздаёт скрытой ручкой — она помечена `@Hidden`
и в Swagger/сгенерированный клиент не попадает:

```
GET  /api/superadmin/users                          → все учётки с ролями
POST /api/superadmin/users  {email, name?, role}    → создать учётку с ролью или сменить роль существующей
```

Назначить можно `CUSTOMER`, `CREATOR`, `FINANCE_MANAGER` или `ADMIN`; почту из
`SUPER_ADMIN_EMAIL` ручка не трогает. Учётка заводится сразу (при необходимости с профилем
и кошельком — `AccountProvisioningService`), человек входит по коду с почты как все.

`SERVICE` **не хранится в БД** (CHECK на `users.role` его не пропустит) — это роль,
которую выдаёт `JwtAuthFilter` тому, кто пришёл с правильным `SERVICE_JWT_TOKEN`
в заголовке `X-Auth-Token` (или `Authorization: Bearer`).

Зарегистрироваться снаружи можно только как `CUSTOMER` или `CREATOR`; почту, за которой
уже закреплена служебная учётка, `register` не перезаписывает даже до подтверждения (`409`).
Профиль нужного типа (и кошелёк у заказчика) заводится пустым сразу при регистрации,
а вход — по коду с почты (см. ниже).

## Авторизация: вход по коду с почты

Паролей нет. Почта — и логин, и способ подтвердить, что она твоя:

```
POST /api/auth/register      {email, name, role}   → учётка + пустой профиль, письмо с кодом
POST /api/auth/request-code  {email}               → письмо с кодом на уже существующую учётку
POST /api/auth/verify        {email, code}         → {token, role, email, name}
```

Код — 6 цифр, живёт **10 минут**, вводить можно **5 раз**, повторно запросить —
не раньше чем через **30 секунд** (`429`). Новый запрос гасит все предыдущие коды
этой почты. Коды лежат в таблице `login_code` (`LoginCodeStore`), письмо шлёт
`EmailService` (реализация `NotiSendEmailService`), HTML берётся из
`resources/templates/email-login-code.html` через `EmailTemplate`.

`register` создаёт учётку сразу, но помечает её подтверждённой (`users.verified_at`)
только после первого `verify`. Пока почта не подтверждена, повторный `register`
с той же почтой не даёт `409`, а перезаписывает имя и роль и шлёт код заново —
так чужая опечатка в адресе не блокирует настоящего владельца.

Без `EMAIL_NOTISEND_API_KEY` письма не уходят: `NotiSendEmailService` печатает
тело письма в лог на уровне `WARN`, откуда на локали и берётся код.

JWT живёт неделю; в нём `sub` (почта), `role` и `name` — фронт рисует шапку
кабинета, не ходя в `/api/auth/me`.

## Фоновые таски

Отложенная работа (например, рассылка писем) не делается в запросе, а кладётся
в таблицу `task` и разгребается по расписанию:

- `TaskAdder.addTask(payload)` сериализует payload в JSON и сохраняет таску со
  статусом `NEW`; тип определяется по классу payload (`TaskType.fromObject`).
- `AbstractRunnableTask` — скелет раннера: раз в `tasks.fixed-rate-ms` забирает
  не больше `tasks.batch-size` тасок своего типа и исполняет их по одной
  (`NEW → RUNNING → DONE`, при исключении `FAILED` с текстом ошибки в `comment`).
- Конкретный раннер наследует скелет и реализует `fetchBatch` + `process`.
  Сейчас есть один: `EmailTaskRunner` для `TaskType.EMAIL` (payload
  `EmailTaskPayload {to, subject, html}`).

Новый вид работы = новый payload-класс, новое значение в `TaskType` и новый
раннер. Дефолт 5 тасок в минуту рассчитан на лимит писем бесплатного тарифа NotiSend.

Правила, которые стоит знать заранее:

- откликнуться можно только на объявление в статусе `ACTIVE`;
- площадка ролика определяется по ссылке и должна входить в `platforms` объявления,
  иначе `400`; сам список площадок обязателен при создании и правке объявления
  (хотя бы одна из `INSTAGRAM`, `TIKTOK`, `YOUTUBE_SHORTS`);
- тот же ролик, поданный повторно (в любое объявление), — `409`
  (в БД стоит `UNIQUE (campaign_id, creator_id)`);
- заказчик не может откликаться на собственное объявление;
- заказчик переводит отклик только в `APPROVED`, `REJECTED` или `COMPLETED`;
- удалить объявление можно, только пока по нему нет откликов;
- бюджет объявления резервируется из кошелька заказчика: при создании и увеличении —
  `409`, если свободных денег не хватает; уменьшение возвращает разницу в кошелёк,
  но ниже уже начисленного криаторам бюджет не опустить (`400`);
- порог вывода (`minPayoutKopecks`) обязателен и больше нуля: пока накопленное
  криатором по объявлению меньше порога, начисления копятся на откликах и в кошелёк
  не попадают;
- требования к ролику необязательны, `null` — без ограничения: `minVideoSeconds`
  только показывается криатору (хронометраж платформа не проверяет); `minPaidViews` —
  порог оплаты: ролик с меньшим числом просмотров получает нулевое начисление, после
  порога оплачиваются все просмотры; `maxVideosPerCreator` — сколько роликов примет
  одно объявление от одного криатора (отклонённые не в счёт), сверх лимита `409`;
  `startsAt`/`endsAt` — период приёма откликов: вне его объявление не показывается
  на доске, а отклик получает `400`, при этом начисления по уже принятым роликам
  продолжаются; `endsAt` раньше `startsAt` — `400`;
- материалы (`materials`, до 10): файл (`kind=FILE`, `fileKey` из
  `/api/files/campaign-material/presign`, имя, тип и размер) или ссылка
  (`kind=LINK`, `url` с `http(s)://`); в ответе у файла `url` — временная ссылка
  на хранилище с исходным именем, `opensInBrowser` говорит, откроется ли файл
  во вкладке (картинка, PDF, видео, аудио) или скачается;
- регион просмотров (`viewRegion`: `RUSSIA`, `CIS`, `WORLD`) обязателен; при `RUSSIA`
  и `CIS` оплачиваются только просмотры из региона, а ролики без известной географии
  не оплачиваются вовсе — см. «Регион просмотров» ниже;
- любое изменение просмотров или статуса отклика запускает пересчёт начислений
  **по всему объявлению**, а не по одному отклику.

## Подсчёт просмотров

Просмотры приносит фоновая задача `ViewsSyncTask` (по умолчанию раз в час,
`VIEWS_SYNC_*`): `ViewsSyncService.syncApproved()` обходит одобренные отклики,
группирует их по площадке и криатору и спрашивает `ViewCountProvider` нужной площадки:

| Площадка | Провайдер | Общие просмотры | География просмотров |
|---|---|---|---|
| YouTube Shorts | `YoutubeViewCountProvider` | Data API `videos?part=statistics` по ключу `YOUTUBE_API_KEY` | Analytics API `reports?dimensions=country&filters=video==…` по OAuth-токену криатора со скоупом `yt-analytics.readonly` |
| TikTok | `TiktokViewCountProvider` | Display API `video/query` по токену криатора | площадка не отдаёт |
| Instagram | `InstagramViewCountProvider` | Graph API `insights?metric=views` по токену криатора | площадка не отдаёт |

Провайдер возвращает `ViewCount`: общее число просмотров и, если площадка это умеет,
разбивку по странам (`byCountry`, коды ISO 3166-1 alpha-2, `ZZ` — страна не
определена). `byCountry == null` — география неизвестна. Каждый замер пишется
в `application_view_snapshot` (историю отдаёт `GET /api/applications/{id}/views/history`);
у отклика `views` только растут (берётся максимум старого и нового), а `country_views`
перезаписывается, когда география известна, — последняя известная разбивка хранится,
пока не придёт новая.

Внешний анализатор может проставить просмотры технической ручкой; разбивка по странам
необязательна, без неё география считается неизвестной:

```bash
curl -X PATCH http://localhost:8090/api/tech/applications/<id>/views \
  -H 'X-Auth-Token: <SERVICE_JWT_TOKEN>' \
  -H 'Content-Type: application/json' \
  -d '{"views": 12400, "countryViews": {"RU": 11000, "KZ": 900}}'
```

Ручка проставляет `views` и `country_views`, отмечает `views_synced_at` и пересчитывает
начисления по объявлению. Коды стран — две буквы, значения не меньше нуля, сумма
не больше `views`, иначе `400`.

### Регион просмотров

У объявления есть `viewRegion`: `RUSSIA` (только РФ), `CIS` (СНГ: RU, BY, KZ, KG, TJ,
UZ, AM, AZ, TM, MD) или `WORLD` (весь мир); список стран задан в `ViewRegion`.
Заказчик выбирает регион при создании объявления, криатор видит его на доске, на
странице объявления и на форме отклика — до публикации ролика.

В расчёт выплаты идут только просмотры из региона — `Application.payableViews(region)`:

- `WORLD` — все просмотры (`views`);
- `RUSSIA` / `CIS` при известной географии — сумма `country_views` по странам региона,
  но не больше `views`; `ZZ` в регион не входит;
- `RUSSIA` / `CIS` при неизвестной географии (`country_views IS NULL`: TikTok, Instagram,
  YouTube без доступа к аналитике, техническая ручка без `countryViews`) — **0**, ролик
  не оплачивается. Это осознанное правило, а не пробел: заказчик платит только за
  подтверждённые просмотры из своего региона. В `ApplicationDTO` это видно как
  `payableViews` и `viewsGeographyKnown`, фронт предупреждает и заказчика в редакторе,
  и криатора перед откликом.

Порог `minPaidViews` сравнивается с оплачиваемыми просмотрами. Смена региона в правке
объявления пересчитывает начисления по всем откликам, как и смена ставки.

YouTube Analytics отдаёт данные с задержкой 48–72 часа, поэтому региональная сумма
отстаёт от общего счётчика и догоняет его со следующими синхронизациями. Аккаунты
YouTube, привязанные до появления скоупа аналитики, географию не отдают — криатору
нужно переподключить канал; `SocialAccountDTO.reportsViewGeography` показывает,
есть ли доступ.

## Деньги

**Всё в копейках.** В БД — `BIGINT`, в API — `Long`, в рубли сумма превращается
только на экране. Никаких `double` и `float`: `35000` — это 350 ₽.

Начисление за один отклик считает `PayoutCalculator.accrual`:

```
начислено = floor(просмотры / 1000 * ставка_за_1000)   // округление ВНИЗ до копейки
начислено = min(начислено, остаток_бюджета_объявления) // бюджет — жёсткий потолок
```

Вниз — потому что платформа не выплачивает больше, чем реально набрано.
Потолок — потому что заказчик не должен внезапно оказаться должен больше,
чем выделил.

`CampaignAccrualService.recalculate(campaign)` пересчитывает объявление целиком
и детерминированно: отклики берутся в порядке `created_at ASC`, для каждого
одобренного (`APPROVED` или `COMPLETED`) считается начисление от текущего остатка,
остаток уменьшается; у `PENDING` и `REJECTED` начисление обнуляется. В конце
`campaign.spent_kopecks` = сумма начислений.

Из этого следует важное: кто откликнулся раньше, тот и получает деньги первым —
если бюджет кончится, «съест» его начало очереди, а не последний пришедший.
Поэтому пересчёт всегда идёт по всему объявлению: тронуть один отклик в отрыве
от остальных нельзя, порядок разъедется.

Шкала бюджета на карточке — это ровно `spent_kopecks` из `budget_kopecks`,
остаток `remainingKopecks` приходит с бэка посчитанным.

### Кошелёк заказчика

У каждого заказчика есть строка в `wallet` с **свободным остатком** `balance_kopecks`,
а каждое движение денег — строка в `wallet_transaction` с суммой со знаком
относительно свободного остатка и остатком после операции:

| Тип | Кто | Сумма | Статус | Что значит |
|---|---|---|---|---|
| `TOP_UP` | менеджер финансов | `+X` | `SENT` → `CONFIRMED`, либо `REJECTED` | заказчик перевёл USDT платформе, финансист зачислил |
| `WITHDRAWAL` | менеджер финансов | `−X` | `SENT` → `CONFIRMED`, либо `REJECTED` | финансист отправил USDT на адрес TRON заказчика из свободного остатка |
| `ALLOCATION` | заказчик | `−X` | `DONE` | бюджет объявления вырос — деньги зарезервированы |
| `RELEASE` | заказчик | `+X` | `DONE` | бюджет объявления уменьшили или объявление удалили |

**Пополнение и вывод — с документами.** Финансист заводит операцию уже по факту перевода:
сумма, номер (хеш) транзакции и хотя бы один скриншот обязательны, для вывода — ещё адрес
TRON заказчика. Деньги двигаются сразу (пополнение доступно к распределению, вывод списан),
операция получает статус `SENT`, а в `transfer` сохраняются документы. Заказчик открывает
операцию в своём кошельке, сверяет и жмёт `confirm` — статус `CONFIRMED`. Если перевод
не сошёлся, финансист из `SENT` делает `reject` с причиной: статус `REJECTED`, деньги
возвращаются туда, откуда пришли. Отклонить пополнение, которое заказчик уже раздал по
объявлениям, нельзя — `409`. Старые пополнения и списания, проведённые до появления
документов, остаются в статусе `DONE` без `transfer`.

Инвариант: `wallet.balance_kopecks` = сумма `amount_kopecks` по кошельку. Все движения
идут через `WalletService`: он берёт строку кошелька под `SELECT … FOR UPDATE`
(`GetterWallet.getByUserIdForUpdate`), проверяет остаток и пишет операцию одной
транзакцией с изменением объявления, так что нехватка денег откатывает и правку объявления.
Резервом занимается только `CampaignService` (`reallocate` на создании и правке,
`releaseBeforeDelete` на удалении); менеджер финансов трогает лишь свободный остаток,
деньги внутри объявлений ему недоступны.

Бюджеты объявлений, заведённых до появления кошелька, миграция `V10` считает
оплаченными: на каждое пишется пара `TOP_UP`/`ALLOCATION` с пометкой в комментарии,
чтобы журнал сходился, а кошелёк не ушёл в минус при уменьшении такого бюджета.

### Кошелёк криатора и вывод USDT

У криатора тот же `wallet`, но операции другие:

| Тип | Кто | Сумма | Статус | Что значит |
|---|---|---|---|---|
| `EARNING` | ночной шедулер | `+X` | `DONE` | разница между `application.accrued_kopecks` и `credited_kopecks` переехала в кошелёк |
| `PAYOUT` | криатор | `−X` | `PENDING` → `SENT` → `CONFIRMED`, либо `REJECTED` / `CANCELLED` | заявка на вывод в USDT (TRC-20) |

**Ночное начисление.** `EarningsCreditTask` по cron (`EARNINGS_CRON`, по умолчанию 03:00
`EARNINGS_ZONE`) зовёт `EarningsService.creditAccrued()`: берутся отклики, где
`accrued_kopecks > credited_kopecks`, по каждому в кошелёк криатора пишется `EARNING`
на разницу и `credited_kopecks` подтягивается до `accrued_kopecks`. Начисления
никогда не уходят в минус: если отклик отклонили после начисления, уже зачисленное
остаётся у криатора. Тот же прогон руками — `POST /api/tech/earnings/credit`.

**Порог вывода объявления.** У каждого объявления есть `campaign.min_payout_kopecks` —
заказчик задаёт его при создании. Ночное начисление сравнивает с порогом сумму
`accrued_kopecks` по **всем** откликам криатора в этом объявлении: пока она меньше,
отклики пропускаются и деньги остаются на них (в `/api/earnings` это
`pendingKopecks`); как только сумма дошла до порога, всё незачисленное уезжает в кошелёк,
и дальше начисления по этому объявлению идут без задержек. Порог у каждого объявления
свой, поэтому общего минимума на заявку нет: вывести можно любую сумму, которая уже
лежит в кошельке. Если объявление закрылось раньше, чем криатор дошёл до порога,
начисленное так и остаётся на откликах.

**Заявка на выплату.** Криатор с доступным остатком подаёт `{amountKopecks, tronAddress}`
(адрес — base58, `T` + 33 символа). Сумма списывается с доступного сразу, операция
получает статус `PENDING`, а в `transfer` сохраняется адрес. Дальше:

- финансист видит заявку в `/api/finance/payouts`, переводит USDT вручную, грузит
  скриншоты через `/api/files/transfer-proof/presign` и отмечает `sent` с номером
  транзакции и скриншотами — статус `SENT`;
- криатор видит номер транзакции и скриншоты в `/api/earnings/operations/{id}` и жмёт
  `confirm` — статус `CONFIRMED`;
- пока `PENDING`, криатор может `cancel`, а финансист из `PENDING` или `SENT` —
  `/api/finance/operations/{id}/reject` с причиной; в обоих случаях статус закрывается,
  а сумма возвращается в доступные.

**Перевод (`transfer`) — общий для всех внешних операций.** У `TOP_UP`, `WITHDRAWAL`
и `PAYOUT` (`WalletTransactionType.isExternal`) к строке `wallet_transaction` привязана
строка `transfer`: адрес TRON (у пополнения пустой), номер транзакции, скриншоты
(`transfer_proof`), комментарий финансиста, причина отказа, кто провёл и когда отправлено,
подтверждено, закрыто. Правило одно: кто переводит — прикладывает документы, кто получает —
подтверждает. Пополнения и выводы заказчику заводит `TransferService`, выплаты криаторам
он же отмечает отправленными и отклоняет; подтверждает заказчик через `WalletService.confirm`,
криатор — через `EarningsService.confirmPayout`.

Инвариант журнала: `wallet.balance_kopecks` = сумма `amount_kopecks` по операциям,
чей статус не `REJECTED` и не `CANCELLED` (`WalletTransactionStatus.countsTowardBalance`).
Возврат не пишется отдельной строкой: `WalletLedger.restore` меняет статус
и возвращает сумму — в списке заявка остаётся одной строкой с итоговым статусом.

### Одна таблица и «откуда → куда»

Все движения денег — заказчиков, криаторов, финансиста — лежат в одной таблице
`wallet_transaction`. Списки (`/api/wallet/operations`, `/api/earnings/operations`,
`/api/finance/operations`, `/api/finance/payouts`) отдают только `OperationRowDTO`:
тип, сумма, статус, дата и две стороны движения `source` → `destination`
(`FlowPointDTO`: `kind` + подпись). Всё остальное — в `OperationDetailDTO` по id.

Стороны считаются из типа операции (`MoneyFlowDTO.of`):

| Тип | Откуда | Куда |
|---|---|---|
| `TOP_UP` | вне платформы | кошелёк заказчика |
| `WITHDRAWAL` | кошелёк заказчика | вне платформы |
| `ALLOCATION` | кошелёк заказчика | объявление |
| `RELEASE` | объявление (или «удалённое объявление») | кошелёк заказчика |
| `EARNING` | объявление | кошелёк криатора |
| `PAYOUT` | кошелёк криатора | TRON-адрес из заявки |

`OperationReader` собирает строки и детали для всех трёх сервисов: адреса TRON для
строк `PAYOUT` подтягиваются одним запросом по списку id, а не по одному на строку.

## Схема БД

Таблицы создаёт Flyway (`src/main/resources/db/migration/`).

| Таблица | Что хранит |
|---|---|
| `users` | учётные записи: логин (e-mail), имя, роль, когда почта подтверждена |
| `login_code` | одноразовые коды входа: срок, попытки, использован ли |
| `task` | очередь фоновых тасок: тип, JSON-payload, статус, ошибка |
| `creator_profile` | профиль криатора: псевдоним, о себе, ссылки на площадки |
| `customer_profile` | профиль заказчика: компания, о компании, контакты |
| `campaign` | объявление: ставка, бюджет, потрачено, порог вывода, статус, регион просмотров, требования к ролику (мин. длина, порог оплачиваемых просмотров, лимит роликов от криатора, период приёма откликов) |
| `campaign_platform` | площадки объявления: с каких криатор может подать ролик |
| `campaign_material` | материалы объявления для криатора по порядку: файл в хранилище (ключ, имя, тип, размер) или ссылка |
| `application` | отклик: площадка, ссылка на ролик, просмотры, просмотры по странам (JSON, `NULL` — география неизвестна), начислено, статус |
| `application_view_snapshot` | история замеров просмотров по отклику: когда, сколько, разбивка по странам, источник |
| `social_account` | привязанные аккаунты соцсетей криатора: токены, скоупы, статус |
| `wallet` | кошелёк заказчика или криатора: свободный остаток в копейках |
| `wallet_transaction` | журнал операций по кошельку: тип, сумма со знаком, остаток после, статус, объявление, кто провёл |
| `transfer` | перевод вне платформы по пополнению, выводу или выплате: адрес TRON, номер транзакции, комментарий финансиста, причина отказа, когда отправлен/подтверждён/закрыт |
| `transfer_proof` | ключи скриншотов перевода |

Все таймстемпы — `TIMESTAMP(6) WITH TIME ZONE`, приложение работает в UTC
(`spring.jpa.properties.hibernate.jdbc.time_zone=UTC`).
