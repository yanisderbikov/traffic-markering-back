# traffic markering — backend

Бэкенд площадки, где **заказчик** публикует объявления на рекламные интеграции,
а **криатор** берёт их в работу: снимает вертикальный ролик и прикрепляет на него ссылку.

Заказчик указывает ставку за 1000 просмотров и выделенный бюджет. По мере набора
просмотров бюджет «съедается»: на карточке объявления видно, сколько выделено,
сколько потрачено и сколько осталось. Все деньги — в рублях, а в БД и API — **в копейках**.

## Архитектура

Слои строго односторонние: `controller` → `service` → `repository`. Контроллер не
знает про JPA, сервис не знает про `JpaRepository`, а Spring Data не вылезает за
пределы `repository.impl`.

```
controller/                   @RestController, только разбор запроса и коды ответов
service/<область>/            public-интерфейс — то, что видят остальные слои
service/<область>/impl/       package-private @Service — реализация
repository/                   public-интерфейсы Getter*/Saver*/*Deleter
repository/impl/              package-private *Manager (@Component) и *Repo (@Repository)
model/                        @Entity
dto/                          то, что уезжает наружу
util/                         чистые функции без Spring
```

Зачем так:

- **Интерфейс отдельно от реализации.** Реализации сервисов объявлены без `public` —
  снаружи пакета их не видно, инжектится только интерфейс. Подменить реализацию
  (или замокать её в тесте) можно, не трогая вызывающий код.
- **`Getter*` / `Saver*` / `*Deleter` вместо одного репозитория на сущность.**
  Сервису, который только читает объявления, достаётся `GetterCampaign` — и он
  физически не может ничего записать. Права видны прямо в списке зависимостей класса.
- **`*Manager` — единственное место, где ловится сбой БД.** Каждый метод оборачивает
  вызов `*Repo` в `try/catch` и превращает любое исключение в
  `RuntimeException("Database exception", e)`, предварительно записав его в лог.
  Поэтому выше по стеку никто не разбирает `DataAccessException` и её наследников.
- **`*Repo` спрятан в `repository.impl`.** Интерфейс Spring Data package-private,
  так что мимо `*Manager` в базу не сходить — обход слоя не скомпилируется.

Исключение одно: `UserRepository` — обычный public `JpaRepository` прямо в
`repository`. Пользователь нужен почти каждому сервису, и заворачивать его
в четыре интерфейса смысла нет.

Ошибки бизнес-логики бросаются как
`ResponseStatusException(HttpStatus.X, "русское сообщение")` — текст уезжает
пользователю как есть, поэтому он сразу пишется по-русски. Ловят их локальные
`@ExceptionHandler` в каждом контроллере и заворачивают в `{"message": "..."}` —
формат, который фронт показывает без перевода.

## Роли

| Роль | Кто это | Что может |
|---|---|---|
| `CUSTOMER` | заказчик | заводит объявления, смотрит отклики, одобряет/отклоняет их |
| `CREATOR` | криатор | откликается на объявления с ссылкой на ролик, видит свои начисления |
| `ADMIN` | администратор | всё, что могут обе роли |
| `SERVICE` | не человек, а внешний анализатор просмотров | только `/api/tech/**` и `/api/actuator/**` |

`SERVICE` **не хранится в БД** (CHECK на `users.role` его не пропустит) — это роль,
которую выдаёт `JwtAuthFilter` тому, кто пришёл с правильным `SERVICE_JWT_TOKEN`
в заголовке `X-Auth-Token` (или `Authorization: Bearer`).

Зарегистрироваться снаружи можно только как `CUSTOMER` или `CREATOR`.
Профиль нужного типа заводится пустым сразу при регистрации, а в ответ приходит
JWT — человек оказывается залогинен без второго запроса.

## Ручки

| Метод | Путь | Кто может | Что делает |
|---|---|---|---|
| POST | `/api/auth/register` | все | регистрация, `201` + токен |
| POST | `/api/auth/login` | все | вход, `200` + токен |
| GET | `/api/auth/me` | любой авторизованный | кто я |
| GET | `/api/public/campaigns` | все | доска: только `ACTIVE`, новые сверху |
| GET | `/api/public/campaigns/{publicId}` | все | карточка объявления |
| GET | `/api/public/creators/{userId}` | все | публичный профиль криатора |
| GET | `/api/campaigns` | CUSTOMER, ADMIN | мои объявления, новые сверху |
| POST | `/api/campaigns` | CUSTOMER, ADMIN | создать объявление |
| GET | `/api/campaigns/{id}` | владелец, ADMIN | объявление целиком |
| PUT | `/api/campaigns/{id}` | владелец | правка объявления |
| PATCH | `/api/campaigns/{id}/status` | владелец | сменить статус |
| DELETE | `/api/campaigns/{id}` | владелец | удалить; `409`, если уже есть отклики |
| GET | `/api/campaigns/{id}/applications` | владелец | отклики по объявлению |
| POST | `/api/applications` | CREATOR | взять объявление в работу |
| GET | `/api/applications/my` | CREATOR | мои отклики |
| PATCH | `/api/applications/{id}/status` | владелец объявления | одобрить / отклонить / завершить |
| DELETE | `/api/applications/{id}` | автор отклика | отозвать, только пока `PENDING` |
| GET | `/api/profile/creator` | CREATOR, ADMIN | мой профиль криатора |
| PUT | `/api/profile/creator` | CREATOR, ADMIN | сохранить профиль криатора |
| GET | `/api/profile/customer` | CUSTOMER, ADMIN | мой профиль заказчика |
| PUT | `/api/profile/customer` | CUSTOMER, ADMIN | сохранить профиль заказчика |
| PATCH | `/api/tech/applications/{id}/views` | SERVICE, ADMIN | проставить просмотры ролика |

Правила, которые стоит знать заранее:

- откликнуться можно только на объявление в статусе `ACTIVE`;
- тот же ролик, поданный повторно (в любое объявление), — `409`
  (в БД стоит `UNIQUE (campaign_id, creator_id)`);
- заказчик не может откликаться на собственное объявление;
- заказчик переводит отклик только в `APPROVED`, `REJECTED` или `COMPLETED`;
- удалить объявление можно, только пока по нему нет откликов;
- любое изменение просмотров или статуса отклика запускает пересчёт начислений
  **по всему объявлению**, а не по одному отклику.

## Подсчёт просмотров

Своего счётчика просмотров у платформы нет и в этой версии не будет: TikTok,
Instagram и Telegram отдают статистику по-разному, а часть — вообще только владельцу канала.

Поэтому в коде есть интерфейс `ViewCountProvider` и его единственная реализация
`ManualViewCountProvider`, которая всегда возвращает `Optional.empty()` — «площадка
пока не поддерживается». Фоновая задача `ViewsSyncTask` по расписанию дёргает
`ViewsSyncService.syncApproved()`, тот обходит одобренные отклики и спрашивает провайдера;
пока провайдер молчит, ничего не меняется — и это штатное поведение, а не поломка.

Реальные цифры приносит внешний анализатор технической ручкой:

```bash
curl -X PATCH http://localhost:8090/api/tech/applications/<id>/views \
  -H 'X-Auth-Token: <SERVICE_JWT_TOKEN>' \
  -H 'Content-Type: application/json' \
  -d '{"views": 12400}'
```

Ручка проставляет `views`, отмечает `views_synced_at` и пересчитывает начисления
по объявлению. Когда появится настоящий провайдер, достаточно будет добавить
вторую реализацию `ViewCountProvider` — остальной код не изменится.

## Деньги

**Всё в копейках.** В БД — `BIGINT`, в API — `Long`, в рубли сумма превращается
только на экране. Никаких `double` и `float`: `35000` — это 350 ₽.

Начисление за один отклик считает `PayoutCalculator.accrual`:

```
начислено = floor(просмотры / 1000 * ставка_за_1000)   // округление ВНИЗ до копейки
начислено = min(начислено, остаток_бюджета_объявления) // бюджет — жёсткий потолок
```

Вниз — потому что платформа не выплачивает больше, чем реально набрано.
Потолок — потому что заказчик не должен внезапно оказаться должен больше,
чем выделил.

`CampaignAccrualService.recalculate(campaign)` пересчитывает объявление целиком
и детерминированно: отклики берутся в порядке `created_at ASC`, для каждого
одобренного (`APPROVED` или `COMPLETED`) считается начисление от текущего остатка,
остаток уменьшается; у `PENDING` и `REJECTED` начисление обнуляется. В конце
`campaign.spent_kopecks` = сумма начислений.

Из этого следует важное: кто откликнулся раньше, тот и получает деньги первым —
если бюджет кончится, «съест» его начало очереди, а не последний пришедший.
Поэтому пересчёт всегда идёт по всему объявлению: тронуть один отклик в отрыве
от остальных нельзя, порядок разъедется.

Шкала бюджета на карточке — это ровно `spent_kopecks` из `budget_kopecks`,
остаток `remainingKopecks` приходит с бэка посчитанным.

```sql
DELETE FROM users WHERE username LIKE 'demo-%@traffic.ru';
```

## Схема БД

Таблицы создаёт Flyway (`src/main/resources/db/migration/`).

| Таблица | Что хранит |
|---|---|
| `users` | учётные записи: логин (e-mail), bcrypt-пароль, имя, роль |
| `creator_profile` | профиль криатора: псевдоним, о себе, ссылки на площадки |
| `customer_profile` | профиль заказчика: компания, о компании, контакты |
| `campaign` | объявление: ставка, бюджет, потрачено, статус |
| `application` | отклик: площадка, ссылка на ролик, просмотры, начислено, статус |

Все таймстемпы — `TIMESTAMP(6) WITH TIME ZONE`, приложение работает в UTC
(`spring.jpa.properties.hibernate.jdbc.time_zone=UTC`).
